Changing the posts as a team

The Okuma post in this repo writes the programs that run Kennewell's machines. One person changing it is easy. Two people changing it at once is how a post ends up with half of one fix and none of the other, and nobody can say which version wrote a given program. Git sorts that out, and this page shows how we use it here.

It follows on from How Git works. If commits, branches and pull requests are new to you, read that first. This page puts the same ideas to work on the posts.

1

What's in the repo, and what stays on your PC

The shared copy lives on GitHub at Kennewell-CNC/kennewell-cnc-posts. Everyone who works on the posts clones it to their own PC and works there. Nearly every change you'll make is to one file, the Okuma post.

In the repo, shared with everyone

  • okuma-kennewell-cnc.cps, the post itself.
  • machines/, the Fusion machine definitions for the GENOS M560V-5AX, the M560 4ax (cyclic and limited), the M460 and the MB-56VII. The post errors without one, so every test post uses one of these.
  • okuma-osp-p500-manual/, the Okuma programming manual split into sections, so a G-code can be looked up rather than guessed.
  • .claude/skills/ and CLAUDE.md, the post-processor know-how Claude works from and the rules it follows in this repo.

Kept off GitHub on purpose

  • Autodesk's Post Processor Guide, the training guide and the Autodesk library posts. They're Autodesk copyright. You can keep your own copies, but they never get committed.
  • Your own working files: local copies or trial versions of a post, reference documents and project folders. The .gitignore file lists the ones we've agreed to keep local, such as the KENNEWELL folder and the Okuma Word documents.
  • Anything else Git lists as untracked that you don't recognise. Ask before adding it.

Git skips anything named in .gitignore, so a careless git add won't send copyright material up to GitHub.

2

main is the production post

Rule number one: main is the production release of every post in this repo. The versions on main are the ones uploaded to the Fusion Hub, so they're what everyone posts with and what ends up on the machines. That's why nothing lands on main until it's been posted, compared against the previous version, checked by a second person and, if it changes how the machine moves, run on the machine.

Up to now one person has made every change, committing straight to main. That's fine when you're working alone. As soon as a second person is changing the post, every change goes on its own branch and arrives on main through a pull request, where someone else checks it before it's merged.

TipWhoever administers the Kennewell-CNC organisation on GitHub can add a rule to main that refuses direct pushes and requires an approved pull request. Then nobody has to remember the rule, because GitHub won't let them break it.

Setting up a new PC

Do this once per person, per PC.

  1. A GitHub account, added to the Kennewell-CNC organisation. Ask the organisation's admin to invite you.
  2. Install the software.
    Git for Windows
    Git itself. It also installs Git Credential Manager, which handles signing in to GitHub (step 4).
    VS Code
    the editor you open the repo folder in, to read and edit the post.
    Claude Code
    does most of the Git work on this page for you, once you're signed in to GitHub.
    GitHub CLI (optional)
    lets Claude open pull requests for you as well. Sign it in once with gh auth login. Without it, Claude pushes your branch and you open the pull request on the GitHub website.
    Fusion
    the regression diff uses the post engine that installs with it.
    Node.js
    runs the regression diff.
  3. Add the VS Code extensions. Open the Extensions panel in VS Code and search for each one by name.
    Autodesk Fusion post processor extension
    edit and test-post .cps files from inside VS Code.
    GitLens
    shows who changed each line of the post, when and in which commit, right in the editor.
    ESLint
    flags JavaScript mistakes in the post as you type, before you ever post with it.
    NC-Gcode
    colours the NC output so programs are easier to read and compare.
  4. Clone the repo, and sign in to GitHub. Open Claude Code in C:\source:
    Ask Claude

    Clone Kennewell-CNC/kennewell-cnc-posts from GitHub into this folder.

    What Claude runs: git clone https://github.com/Kennewell-CNC/kennewell-cnc-posts.git

    Because it's the first time Git has talked to GitHub, Git Credential Manager opens your browser to sign in, then saves the sign-in in Windows Credential Manager. You only do this once. If it ever stops working (a changed password, say), remove the github.com entry from Windows Credential Manager and Git asks you to sign in again.

    You can also clone over SSH (git@github.com:Kennewell-CNC/kennewell-cnc-posts.git), which signs in with a key on your PC instead. Either works with the same repo.

  5. Hand the rest to Claude. Open Claude Code in the new kennewell-cnc-posts folder and ask it to finish the setup:
    Ask Claude

    Set my Git name to Jo Bloggs and my email to the one on my GitHub account, then check the regression diff can find Fusion's post engine.

    What Claude runs: git config --global user.name "Jo Bloggs" git config --global user.email … node .claude/skills/post-regression-diff/scripts/post-diff.js doctor

The key thingOnce you're signed in to GitHub, Claude Code can do nearly all the Git work on this page. You tell it what you want in plain English, and it pulls, branches, commits, pushes and runs the regression diff for you. The machining judgement stays with you. You decide what the change should do and whether the NC is right, and you do the prove-out on the machine yourself.

4

The life of a post change

Every change follows the same nine steps. Each one has an example of what to ask Claude Code. Underneath, in small print, are the Git commands Claude runs in the background, so you can follow what it's doing and recognise them when it reports back.

  1. Start from the latest main

    Otherwise you're building on whatever was there the last time you pulled, which could be last week's post.

    Ask Claude

    Switch to main and pull the latest from GitHub.

    What Claude runs: git switch main git pull

  2. Make a branch named after the job

    Keep it to one change per branch, like one G-code fix or one new property. If it turns out to be wrong, it can be backed out without taking anything else with it.

    Ask Claude

    Start a branch for adding G97 after every work offset.

    What Claude runs: git switch -c okuma-g97-after-work-offset

  3. Make the change

    Describe it the way you'd explain it to another machinist: which machine, which code, where it goes in the program, and the manual page if you have one. Claude edits the post in its existing style and tells you about anything that changes modal behaviour, because those are the changes that look like one word in the code but alter every program.

    Ask Claude

    In the Okuma post, output G97 on its own line after every G15 H work offset. The manual says it's a one-shot code that mustn't share a block with axis motion (P-27, P-57 and P-551). Tell me if anything modal changes.

  4. Prove it with the regression diff

    Post the same test programs through the old post and your edited one, and compare the NC. Chapter 5 covers this properly.

    Ask Claude

    Run the regression diff against main for the M560 4ax cyclic and the GENOS 5-axis, and show me every NC line that changed.

    What Claude runs: node .claude/skills/post-regression-diff/scripts/post-diff.js diff --ref main --machine …

  5. Commit, with a message that says what the machine will do differently

    Ask Claude

    Commit the post change. Say what the machine does differently and how we checked it.

    What Claude runs: git add okuma-kennewell-cnc.cps git commit

    Read the message before it goes in. The first line is a short summary, and the rest says why the change was made and how it was checked. Here's one from the repo's own history, shortened:

    Okuma post: G97 after every work offset

Output G97 (coordinate recalculation function, P-551) in its own block
after every G15 H__ work offset selection, as recommended by Okuma.
G97 is one-shot and must not share a block with axis motion (P-27, P-57).

Verified against the previous commit on the GENOS M560V-5AX with each
tilted plane method, and on the M560 4ax cyclic: every G15 line is
followed by exactly one G97 and no other line moves.

    If Claude says it's about to commit a file you don't recognise, stop it. Only the files the change is in should go in.

  6. Push the branch and open a pull request

    The description should say which machines were posted for and include the regression diff summary, so the reviewer starts with the evidence.

    Ask Claude

    Push this branch and open a pull request. Put the regression diff summary and the machines we posted for in the description.

    What Claude runs: git push -u origin okuma-g97-after-work-offset gh pr create (needs the GitHub CLI)

  7. Get it reviewed

    A second person reads the NC changes as well as the code, and approves or asks for changes. Chapter 6 is the reviewer's checklist. If changes are needed, make them on the same branch and push again. The pull request updates itself.

    Ask Claude

    The reviewer wants the G97 left out of the OYZ routine. Make that change, re-run the regression diff, then commit and push.

    What Claude runs: post-diff.js diff … git add okuma-kennewell-cnc.cps git commit git push

  8. Prove it on the machine

    This step is yours. If the change alters motion, work offsets, tool change, retracts, the rotary axis or tilted planes, run a program posted from the branch with your usual first-run caution: single block, rapid and feed overrides down, hand near feed hold. A change to comments or the program header doesn't need this. Note in the pull request what you ran and on which machine.

  9. Merge, upload to the Fusion Hub, and tag

    Merge the pull request on GitHub. Upload the post from main to the Fusion Hub, never from a branch, so nobody ends up posting with unreviewed work. Then tag the release (chapter 8) and tidy up.

    Ask Claude

    The pull request is merged. Switch back to main, pull, tag it as okuma-2026-10-16, push the tag and delete the finished branch.

    What Claude runs: git switch main git pull git tag okuma-2026-10-16 git push origin okuma-2026-10-16 git branch -d okuma-g97-after-work-offset

5

Proving a change with the regression diff

You can read a code change carefully and still not know what it does to the NC. The regression diff shows you. It takes the post as it was before your edit and the post as you've edited it, posts the same set of test programs through both for the machine you pick, and compares the NC files line by line.

You get one of three results:

CLEAN
every NC file came out identical. That's right for a tidy-up that shouldn't change output. If you meant to change something, either the change didn't take effect or the test programs never reached it.
DIFFERENCES
some files changed. Open each one and check that only the lines you intended moved.
FAIL
a program that posted before now errors. Something is broken. Fix it before going any further.
Ask Claude

Run the regression diff against main for the M560 4ax cyclic and the GENOS 5-axis.

What Claude runs: node .claude/skills/post-regression-diff/scripts/post-diff.js diff --post okuma-kennewell-cnc.cps --machine "Okuma M560 4ax cyclic" --ref main --category Milling, then the same again for the GENOS.

The key thing to understand is that a post shares its number formats and modal state across every operation. Edit one corner of the code and you can change every feed, or every rapid, in every program without meaning to. That's what the diff is there to catch, because you'd rarely spot it by reading the code.

6

Reviewing someone else's change

Approve only when you'd be happy running it on your own job. Work through these on the pull request page:

  1. Does the description say what the machine will do differently, and on which machines? If you can't tell from the description, ask before you read the code.
  2. Does the regression diff match the description? Every changed NC line should trace back to it. If the pull request doesn't include the diff, run it yourself (below).
  3. Were the right machines posted? A change to tilted-plane code needs posting on the GENOS M560V-5AX with each tilted-plane method, not only on a 4-axis machine.
  4. Is it one change? Two unrelated changes in one pull request are harder to check and can't be backed out separately. Ask for them to be split.
  5. Does it need a machine prove-out, and has it had one?

Leave comments on the exact lines on GitHub, the same way you'd mark up a drawing. To run the diff on someone's branch yourself:

Ask Claude

Check out okuma-g97-after-work-offset and run the regression diff against main for every machine it affects.

What Claude runs: git fetch git switch okuma-g97-after-work-offset post-diff.js diff --ref main …

Extra careTake extra care with changes to the rotary axis, tilted work plane, work offset, retract and tool change code. Get a comment wrong and you get a wrong comment. Get one of these wrong and the machine goes somewhere you didn't expect, possibly with a tool in the cut.

7

Two people, one post file

Because almost everything lives in one file, conflicts are more likely here than on most projects. Git can combine two edits to different parts of the post on its own. It can't combine two edits to the same lines, so it stops and asks you to choose (How Git works, chapter 6, shows what that looks like).

These keep conflicts rare and small:

  • Say what you're working on. Open your pull request early as a draft, so the other person can see which part of the post you're in.
  • Keep branches short. A branch that lives for a day rarely conflicts. One that lives for a month nearly always does.
  • Bring main into your branch before asking for review, then re-run the regression diff. The other person's change is in main now, and you want to know yours still behaves with it in there.
    Ask Claude

    Bring main into my branch and re-run the regression diff. If there's a conflict, show me both versions of the lines and explain the difference before changing anything.

    What Claude runs: git switch okuma-g97-after-work-offset git merge main post-diff.js diff --ref main …

  • Don't reformat code you aren't changing. Re-indenting or tidying makes every line look changed and almost guarantees a conflict. The repo's rules already tell Claude not to.

StopIf Git says every line of the post has changed, what's really changed, almost every time, is the line endings. The repo stores .cps and .nc files one way and gives you Windows line endings on your PC, which is what the controls expect. Don't commit it. Ask Claude to check what happened.

8

Which post cut this part?

When a part comes off wrong, one of the first questions is which version of the post wrote the program. Tags answer it. A tag is a permanent name on one commit, like a revision letter on a drawing. Each time you upload a new version to the Fusion Hub, tag main and send the tag to GitHub:

Ask Claude

Pull main, tag it as okuma-2026-10-16 and push the tag.

What Claude runs: git switch main git pull git tag okuma-2026-10-16 git push origin okuma-2026-10-16

The date-based name is a suggestion. Any scheme works, as long as everyone uses the same one. If two releases go out on the same day, add a letter.

The regression diff can then compare against any release, which shows exactly how today's post differs from the one that cut that part:

Ask Claude

Compare today's post against the okuma-2026-10-16 release on the M560 4ax cyclic.

What Claude runs: post-diff.js diff --ref okuma-2026-10-16 --machine "Okuma M560 4ax cyclic" …
